## 1. 结论摘要

本次公共链路显示的不是战败、俘虏、市场交易或服主重置，而是一笔由玩家账号发出的、通过签名及顺序校验的“从格子移除已部署将领”地图变更。它与当前 `recall-general` 规则产生的数据形状完全一致。

- 玩家账号 ID：`17fa4f94-40bd-4ada-b3c3-30b9ac821aed`
- 玩家显示名：`yuoa333`
- 原部署坐标：`(16,3)`

- 部署记录完整：2026-09-20 09:01:28
- 召回记录：2026-09-20 09:01:49
- 从部署完成到召回：约 21 秒
- 召回后的公共状态：格子仍归原玩家、士兵仍为 0、`generalIds` 由江玖鸢变为空数组、江玖鸢公共档案被置为 `null`

判断如下：

1. **公共地图上的“瞬间消失”可稳定复现。** 这是召回后的预期公开投影：随行将领属于玩家私有数据，不再出现在公共地图中。
2. **正常完成召回时，将领实体仍应存在。** 规则会把江玖鸢改为 `carried`，加入玩家的 `carriedGeneralIds`，仅从部署格和公共投影移除。
3. **单纯操作很快不会直接删掉将领。** 1 毫秒间隔的最小复现仍保留了将领；第二次召回也会被状态校验拦截。
4. **存在一个真实的持久化风险窗口。** 当前顺序是先把公共删除记录发布到远端，再把私有随行状态保存到本机。若在远端已接收记录、而本地尚未落盘的短窗口内发生强制结束、断电、磁盘写入故障或进程崩溃，重启后可能呈现“公共档案已删除，本地私有档案也没有”的真实丢失。
5. **现有服主指令没有代玩家部署或恢复单个将领的入口。** 本次诊断未向线上写入任何修复记录。推荐先检查玩家原设备、原账号配置的本地缓存；若江玖鸢仍在随行列表，让玩家回到 `(16,3)` 自行部署即可。若本地档案缺失，应先通过专用恢复流程重建私有档案，再由玩家发起部署。

## 3. 代码链路

### 3.1 前端入口

已部署将领卡片在玩家位于同一格时直接显示“召回”按钮：

```text
electron/desktop/online-world/grid-conquest/game.js:1645-1651
```

当前按钮点击后直接发送 `recall-general`，没有二次确认。相比部署操作，部署已有确认弹窗和提交中禁用状态：

```text
electron/desktop/online-world/grid-conquest/game.js:2684-2698
```

因此误触风险主要集中在召回按钮，而不是部署确认按钮的重复提交。

### 3.2 消息桥与并发控制

游戏 iframe 通过 `postMessage` 发送意图，宿主校验消息来源窗口、协议和请求 ID，再交给联机服务：

```text
electron/desktop/renderer.js:1451-1467
electron/desktop/renderer.js:1549-1570
```

前端用 `intent:<type>` 对同类在途请求去重；服务端也只允许一个玩家意图在途，并通过 `idempotencyKey` 防止同一意图重复执行：

```text
electron/desktop/online-world/grid-conquest/game.js:66-96
electron/desktop/online-world/grid-conquest/game.js:2474-2476
electron/online-world-service.cjs:2988-3027
```

所以网络重试、双击部署确认或同一请求的重复返回，不会自行生成这笔召回。合法的 iframe 程序、UI 自动化或复制了同一设备身份的客户端仍可主动发送一笔新的召回意图；现有公共记录没有记录 `inputSource`，仅凭远端账本区分不了“手指/鼠标点击”和“程序化触发”。

### 3.3 规则执行

召回规则执行四个关键动作：

```text
electron/grid-world-game.cjs:2089-2101
```

1. 校验将领由当前玩家持有，且位于玩家当前格。
2. 从格子的 `generalIds` 移除将领 ID。
3. 把将领 ID 加入玩家的 `carriedGeneralIds`。
4. 将状态改为 `carried`，位置改为 `null`。

这里没有删除将领实体的语句。

### 3.4 公共投影为何显示“消失”

公共投影只收录 `status === "deployed"` 的将领。将领被召回后，公共差异生成器会把该档案写成 `null`：

```text
electron/online-world-service.cjs:300-320
```

其他客户端应用该差异时会删除公开档案：

```text
electron/online-world-service.cjs:2440-2469
```

因此其他玩家、服主视图以及公共快照看到江玖鸢消失，是私有化后的正常表现，不足以单独证明将领实体已丢失。

### 3.5 真正的数据风险窗口

本地意图处理顺序为：

```text
applyIntent（内存改为随行）
  -> publishMapChanges（远端发布公共删除）
  -> handleEffects
  -> saveCache（本地保存随行档案）
```

对应位置：

```text
electron/online-world-service.cjs:3129-3155
electron/online-world-service.cjs:3207-3221
```

同时，正常缓存会主动剔除已部署将领，部署档案依靠公共账本恢复；本地 overlay 只保存当前玩家的非部署将领：

```text
electron/online-world-service.cjs:340-345
electron/online-world-service.cjs:987-1013
electron/online-world-service.cjs:1267-1273
```

这形成以下故障序列：

1. 召回前的旧缓存里不含江玖鸢完整档案，因为她当时处于部署状态。
2. 召回意图在内存中将她转为随行。
3. 远端成功收到“删除公共档案”的地图变更。
4. 本地 `saveCache()` 尚未完成时进程异常结束或写盘失败。
5. 重启后，旧缓存没有江玖鸢，远端最新状态也已删除她的公共档案。
6. 同步结束后，玩家视图里确实找不到该将领。

正常退出路径会保存缓存，`pause()` 还会等待在途意图完成，因此主要风险来自强制结束、断电、系统崩溃、磁盘故障，以及发布成功后落盘前的异常。

### 4.2 可复现性矩阵

| 场景 | 可复现性 | 预期结果 | 诊断意义 |
| --- | --- | --- | --- |
| 正常部署后立即召回 | 稳定 | 公共地图立即移除，玩家随行列表保留 | 正常行为 |

| 同设备身份被复制后在另一客户端操作 | 有条件可复现 | 仍表现为该玩家的有效签名操作 | 需查玩家设备与配置副本 |
| 公共发布成功后强制终止进程 | 预计可稳定复现真实丢失 | 远端已删除，旧本地缓存缺少私有档案 | 应新增故障注入测试确认并锁定修复 |

## 5. 除误触外的可能原因

按本次证据匹配度排序：

1. **二次物理输入。** 部署完成、确认框关闭并刷新卡片后，玩家又产生了一次点击或触摸；召回按钮没有确认步骤。
2. **自动化输入。** 鼠标宏、触控辅助、连点器或 UI 自动化在部署完成后点击了新出现的召回按钮。
3. **游戏程序主动发意图。** 宿主允许当前已加载的合法游戏 iframe 发送 `intent`。若玩家端加载的是修改版、旧版或被替换的游戏程序，它可以程序化发送召回。
4. **同一设备身份的配置副本。** 若另一个客户端持有同一设备签名私钥，它发出的操作在公共链路上仍会表现为该玩家的有效操作。
5. **持久化窗口导致“召回后真丢失”。** 召回已经有效发生，随后本地随行档案没有成功落盘。这最能解释“公共记录像正常召回，但玩家自己的随行列表也找不到江玖鸢”。

以下原因可信度低：服务器自动召回、普通同步覆盖、战斗结算、市场交易、重复网络包。当前代码中没有自动召回定时器，现场数据形状也不匹配这些路径。

## 6. 瞬间召回是否容易造成将领消失

需要区分两个“消失”：

### 6.1 从公共地图消失

**很容易，而且是设计行为。** 召回一经发布，其他客户端就会删除该将领的公开档案。时间间隔再短也不会改变这一点。

### 6.2 从玩家自己的存档消失

**正常流程下概率低。** 规则会把将领转入随行，本次 1 毫秒复现也成功保留。

**遇到异常退出或落盘故障时存在明确风险。** 风险来源是“远端删除先提交、本地私有状态后保存”，而不是“召回太快”这一时间差本身。部署后马上召回会让同一将领在很短时间内连续经历公开化与私有化，因而更容易暴露这类持久化边界问题。

## 7. 玩家恢复与重新部署方案

### 7.1 当前能否由服主直接远程部署

当前服主接口只包含开服、迁移、散落宝物、玩家重置、封禁及解封，没有“恢复单个将领”或“代玩家部署”指令：

```text
electron/online-world-service.cjs:3476-3515
```

普通部署还要求动作由当前登录玩家执行，并使用其设备身份签名。直接伪造一笔公共部署差异会绕过玩家私有状态，容易产生重复档案、持有人不一致或下一次同步回退。

结论：**当前线上版本不宜直接由服主写一条地图记录把江玖鸢放回 `(16,3)`。** 应先恢复玩家私有档案，再让玩家发起合法部署；或者先上线带审计和幂等保护的服主恢复指令。

### 7.2 首选恢复流程：玩家本地档案仍存在

1. 让玩家使用事故时的原设备、原风月账号配置进入同一赛季。
2. 在任何同步、清缓存或重装之前，备份联机世界缓存及其备份文件。
3. 检查玩家自己的 `carriedGeneralIds` 与 `localOverlay.generals` 是否包含：

   ```text
   4858a325-ea7b-4cd0-8597-fcc2ccd1751d
   ```

4. 若存在且状态为 `carried`，让玩家移动到 `(16,3)`。
5. 玩家从随行将领界面正常部署江玖鸢。
6. 核验新 map delta：格子 `generalIds` 包含该 ID，公共将领档案非空，持有人仍为原玩家。

### 7.3 缓存缺失时的恢复流程

公共历史里的部署记录仍保存江玖鸢的完整公开档案，因此具备恢复来源。执行恢复前应验证：

- 来源记录是上述部署 map delta，签名与分片完整。
- 后续移除记录由同一玩家发出，格子归属未变化，且没有战斗、成交、重置或更高玩家纪元。
- 当前赛季中没有同 ID 的新档案、市场条目或俘虏状态。
- 恢复目标账号仍是原持有人。

建议实现一条幂等的 `general-restore` 权威指令，最小载荷如下：

```json
{
  "type": "general-restore",
  "restoreId": "UUID",
  "targetAccountId": "17fa4f94-40bd-4ada-b3c3-30b9ac821aed",
  "playerEpoch": 0,
  "generalId": "4858a325-ea7b-4cd0-8597-fcc2ccd1751d",
  "sourceMapDeltaId": "6fe5bb00-9305-4589-9311-f66c2c30bc46",
  "sourceRemovalMapDeltaId": "ea30da2a-ea25-439a-bdc1-7d74b99b1bdc",
  "restoreMode": "carried",
  "target": { "x": 16, "y": 3 }
}
```

处理原则：

1. 由服主身份签名，客户端验证作者身份、赛季、玩家纪元和来源记录。
2. 默认先恢复为 `carried`，由玩家确认后自行部署。
3. `restoreId` 与 `generalId` 双重幂等；重复执行只返回既有结果。
4. 检测到同 ID 已存在时停止写入并生成冲突报告。
5. 恢复前后都保存只读审计快照。
6. 成功后核验玩家私有档案、随行列表、格子列表和公共档案四处的一致性。

在该指令上线前，可在玩家原设备上进行一次性缓存修复：先完整备份，再把从历史部署记录恢复出的档案写入该玩家的 `localOverlay.generals`，状态设为 `carried`，同时把 ID 加入 `carriedGeneralIds`；重启验证后由玩家正常部署。此操作应由专用脚本完成，并保留修改前后校验摘要，避免手工编辑 JSON 造成结构错误。

## 8. 代码修复建议

### P0：召回二次确认

召回采用与部署一致的确认弹窗，显示将领名和当前位置。确认按钮提交后立即禁用，直到宿主返回结果。对触摸设备增加短暂防连击间隔。

验收标准：

- 单击“召回”只打开确认框。
- 连点、按住、触控抬起均只生成一个请求。
- 请求处理中所有召回入口都保持禁用。
- 成功提示明确写“已召回至随行将领”，并提供进入随行列表的入口。

### P0：持久化事务日志

在发布任何会把私有实体从公共投影移除的变更前，先写入本地 pending transaction，至少保存：

```text
transactionId
intentType
idempotencyKey
beforeStateHash
afterPrivateState
plannedMapDeltaId
phase = prepared | published | committed
```

推荐顺序：

1. 计算变更并生成固定 `mapDeltaId`。
2. 原子写入 `prepared`，其中含恢复江玖鸢所需的私有档案。
3. 发布公共 map delta。
4. 标记 `published`，保存远端顺序和根评论 ID。
5. 原子保存正式缓存。
6. 标记 `committed` 并清理事务日志。

启动时若发现未完成事务：查询远端是否存在该 `mapDeltaId`；存在则完成本地私有提交，不存在则回滚或重试发布。这样可覆盖“远端成功、本地未保存”的崩溃窗口。

### P1：输入来源审计

仅在本地诊断日志增加以下字段，并从公开世界状态中排除：

```text
requestId
intentType
generalId
inputSource = pointer | keyboard | automation | programmatic | unknown
programDigest
clientVersion
profileIdHash
startedAt / publishedAt / persistedAt
```

公共记录可增加不敏感的 `clientActionId` 与 `clientVersion`。这能区分物理误触、程序主动调用和旧版客户端问题。

### P1：恢复工具

## 11. 最终回答

- **这个问题还会出现吗？** 公共地图上的瞬间消失可稳定复现，属于召回投影行为；玩家私有档案真丢失在正常流程下概率低，但当前持久化顺序存在可再次触发的异常窗口。
- **除了误触还有什么可能？** 自动化输入、修改或旧版游戏程序主动发意图、持有相同设备身份的另一客户端，以及召回后的本地落盘故障。
- **瞬间召回是否容易造成将领消失？** 公共视图会立即消失；玩家正常存档应保留。快速本身不是删除原因，异常终止与落盘窗口才是关键风险。
- **是否能远程部署回原位？** 当前线上接口没有服主代部署能力。本次诊断保持线上状态原样；完成玩家缓存检查后，优先由玩家部署。若私有档案缺失，先执行带签名、审计和幂等保护的恢复流程，再部署到 `(16,3)`。
