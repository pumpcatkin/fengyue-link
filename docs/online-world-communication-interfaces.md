# 在线游戏世界通讯接口总表

> 当前宿主协议：`fyow-host/1`  
> 当前公共评论编码：`§FYOW3§`  
> 游戏：`cc.aiero.fyow.grid-conquest`（猎艳疆土）  
> 更新日期：2026-09-17

本文是游戏前端、桌面宿主、风月平台评论区/私信和伴生作品模型之间的通讯单一索引。游戏程序始终运行在断网沙箱中，不接触账号令牌、Cookie、平台接口或文件系统；所有外部通讯都必须交给桌面宿主。

## 1. 完整链路

```text
游戏单文件前端
  └─ postMessage / fyow-host/1
      └─ 桌面渲染层
          └─ 受信 IPC
              └─ OnlineWorldService
                  ├─ /console/api/comments/*      公共地图账本与世界聊天
                  ├─ /console/api/chats/*         加密将领书信
                  ├─ /go/api/apps/chat-messages  伴生作品模型
                  ├─ /console/api/apps/*          作品配置与迁移
                  └─ /go/api/account/profile      平台时间校准
```

状态职责固定如下：

- 评论区：公共领地、驻军、已部署将领档案、奇珍刷新/领取、世界聊天、服主封禁/重置/搬迁指令。
- 平台私信：由将领互动触发的一对一加密书信正文。
- 本地存档：金币、玩家位置、行军队伍、任务、性取向、性癖标签、未部署将领、私人互动历史和待重试模型任务。
- 伴生作品模型：玩家设定整理、将领生成、普通互动、俘虏互动、记忆压缩等结构化任务；模型不保存权威游戏状态。

## 2. 游戏前端与桌面宿主

### 2.1 请求信封

```json
{
  "source": "fyow-grid-conquest",
  "protocol": "fyow-host/1",
  "type": "intent",
  "requestId": "UUID",
  "intent": {}
}
```

宿主同时校验：消息必须来自当前游戏 iframe、`source` 和 `protocol` 必须精确匹配、需要回包的请求必须带 UUID、序列化后不得超过 128 KiB。游戏前端也只接收 `event.source === parent` 的宿主回包。

需要回包的类型：

| type | 载荷 | 用途 |
| --- | --- | --- |
| `intent` | `intent` | 提交一项本机游戏行动 |
| `preferences` | `preferences` | 保存本机性取向和性癖标签 |
| `admin` | `command` | 作品作者执行开服、迁移、重置、封禁与解封 |
| `direct` | `message` | 预留的受控定向消息入口；猎艳疆土界面没有手动发送框 |

不需要业务回包的类型：

| type | 用途 |
| --- | --- |
| `ready` | 前端启动完成，请求宿主推送完整状态 |
| `library` | 返回在线游戏世界游戏库 |

### 2.2 回包信封

```json
{
  "source": "fengyue-host",
  "protocol": "fyow-host/1",
  "type": "result",
  "requestId": "与请求相同的 UUID",
  "result": {}
}
```

失败时 `type` 为 `error`，正文为 `message`。后台状态推送使用 `type: state`，不带请求号。确认框被用户取消时返回 `{ "cancelled": true }`，确保按钮结束等待状态。

同一前端操作在回包前只允许存在一次；重复点击不会生成第二个行动。服务层还会串行化所有玩家行动，避免评论区同步、模型请求和本地状态同时改写世界。

### 2.3 玩家行动

公开前端可提交：

- `join`
- `start-mining`、`stop-mining`
- `train`、`power-train`
- `march`
- `deploy-general`、`recall-general`、`take-general`
- `talk-general`
- `cultivate-general`，提交将领、金币投入与素材种类进行本地修炼
- `world-chat`，载荷为 `{ "type": "world-chat", "text": "纯文本消息" }`
- `quote-march`，只读询价：`{ "type": "quote-march", "to": { "x": 1, "y": 2 }, "soldiers": 0, "generalIds": [], "attack": false, "requestKey": "悬停目标键" }`

`quote-march` 返回 `{ "marchQuote": { "...": "引擎询价字段", "requestKey": "原请求键" } }`。费用和耗时由与实际行军相同的引擎计算，包含目的地、携带将领、地形和天赋影响；不写评论、不修改世界，也不占用普通行动的串行锁。前端用 `requestKey` 丢弃已经离开的悬停目标回包。

宿主内部使用但不接受游戏卡任意构造：

- `record-general-dialogue`
- `surrender-general`
- `grant-general`

每项行动都带 `idempotencyKey`。公共地图写入失败时，世界、本地事件和入场偏好统一回滚；公共地图已经成功提交后，后续将领生成失败会进入本地待重试队列，界面明确显示“领地变化已经生效”，避免玩家重复行动。

## 4. 评论区公共账本

### 4.1 平台接口

```text
POST /console/api/comments/{workId}/1
GET  /console/api/comments/{workId}/1?page={page}&limit=50&order=desc&filter_type=all
GET  /console/api/comments/branches/{rootCommentId}
GET  /console/api/comments/branches/{rootCommentId}?page={page}&limit=50
```

所有新写入的评论均限制为 980 字符，包含分片头和续接标记。记录先做 JSON 规范化、gzip、Base64URL 和 SHA-256，再按 `§FYOW3§类型§记录ID§分片/总数§摘要§内容` 切片；还有后续内容的分片以 `§CONTINUE§` 结尾，最后一片没有续接标记。

第一片写为根评论，其余片使用同一平台评论接口并带 `parent_id: 根评论ID`、`to_account_id: 根评论作者账号`，写入根评论下的原生回复。已经指定回复入口的记录（如将领书信唤醒）保持在该入口分支内。根评论缺少平台返回的 ID 时停止后续分片；平台回包正文被截断或作者不一致时，本机也不应用记录。

2026-09-17 的真实平台验证确认：上述回复写入成功，但 `branches` 接口可能返回空数组；主评论列表的根评论对象会通过 `children` 返回这些原生回复。读取端优先展开主列表的 `children/replies`，为所有后代保留 `_fyowRootId` 来源关系；命中评论后只遍历回复容器，不遍历账号资料、勋章等元数据，因此大回复列表不会被账号对象遍历上限截断。内嵌分片已经完整时不再请求分支；缺片时尝试回复分页，并在分支空或仍缺片时按持久化根评论页索引回读主列表。

展开函数 `extractCommentItems()` 仍返回数组，同时带非枚举的 `rootCount` 和 `rootIds` 分页元数据。分页尾页、页序判断和聊天增量水位只计算根评论；例如一页包含 1 个根评论和 120 条回复，其展开长度为 121、分页条数仍是 1。根评论页索引最多保留 2000 项。

只组装同一作者、同一根分支、分片完整且摘要一致的记录，并验证正文的 Schema/ID 与分片头一致。最大 512 片、解压后最大 8 MiB。旧版没有续接标记、每片都是根评论的 FYOW3 记录和历史 1000 字符评论保持可读。

每个评论分片写入遇到暂时错误时最多重试三次。中途仍失败会让本次公开提交整体失败；残留的不完整分片不会被其他客户端应用。

| `fyow.snapshot/3` | `SNAP` | 作者签名的公共地图覆盖快照 |
| `fyow.map-delta/1` | `MAP` | 一次领地、驻军、已部署将领或奇珍领取变化 |

`fyow.intent/3`、`fyow.event/3`、`fyow.private-vault/3`、`fyow.general-definition/3`、`fyow.general-memory/3` 和评论内 `fyow.direct/3` 只保留在协议解析器中用于旧记录兼容；当前版本不再写入这些内容。

### 4.3 顺序、覆盖与分页

- 所有玩家操作先后以平台根评论时间戳为主、根评论 ID 为次序；后续分片回复的时间戳不改变逻辑记录的顺序。
- 每个格子、已部署将领和参与者分别保存最后应用顺序，旧记录不能覆盖新记录。
- 封禁账号的地图记录被忽略；玩家重置后旧 `playerEpoch` 的记录被忽略。
- 作者每累计 32 条公共增量写入覆盖快照。客户端读取到完整的新快照后，可以跳过被其完全覆盖的旧页面。
- 新快照签名内容含 `ledgerCoverage`：`version: 1`、`through: {timestamp, commentId}`、格子/将领/玩家/行政指令的来源顺序、已包含增量与行政 ID，以及未完成覆盖的奇珍来源证据。`through` 仅表示已完整读取并处理的账本前缀，绝不直接采用快照根评论的发布时间；同时间戳的边界记录保守留在前缀之外。根已出现但回复未齐时，水位停在最早未齐根之前。
- 加载快照后，客户端继续读取并回放 `through` 之后的记录，即使其根时间早于快照发布。逐项来源顺序防止这些回放覆盖快照中已包含的较新操作，已包含 ID 防止重复行政执行。奇珍撤下前已经发布的有效领取仍可凭保留的作者来源证据结算；撤下后才发布的旧批次领取被拒绝。
- 没有 `ledgerCoverage` 的旧快照不被视为完整覆盖水位，客户端保守回读有界历史。已有 `playerEpoch` 拒绝重置前的增量；相同或较旧代数的重置记录不会再清空玩家或推进一次代数，因此不会把重置前的数据重新带回。
- 平台可能忽略 `order=desc`，返回旧到新或混合排序页面。客户端先用持久化尾页提示与指数探测定位真实最后一页，再比较首页与尾页根评论时间戳确认方向；严格旧到新时从尾页回扫，严格新到旧时从首页向后扫描。若检测为 `mixed`，每轮仍全扫有界历史，避免靠时间启发式漏掉散落在其他页面的新评论。
- 全量读取上限 10000 页；尾页编号和最近 500 个评论 ID 保存在本地，平时只检查尾页附近，在已知记录或覆盖快照处提前停止。跨页分片未组装完整时继续读取更旧页面。

### 4.4 世界聊天

前端通过普通行动入口提交 `world-chat`，服务回包仍是包含 `state` 的标准行动结果。宿主状态中的 `worldChat` 是最多 50 条消息的数组，按平台根评论时间从旧到新排列，每项为：

```json
{
  "messageId": "稳定的消息编号",
  "displayName": "玩家设定名",
  "text": "纯文本",
  "createdAt": 1789621200000,
  "accountId": "仅内部识别使用"
}
```

界面只显示 `displayName`，不显示账号 UUID；正文作为文本节点渲染，不作为 HTML 执行。单条正文最多 500 个 Unicode 字符，拒绝空消息、控制字符和 HTML 标签尖括号。每台设备每分钟最多发送 12 条，不调用伴生作品模型，不消耗模型积分。

记录绑定作品、游戏、赛季、玩家账号和重置代数，并验证玩家签名、所有分片的平台来源账号以及玩家已登记的设定名。封禁账号的消息和重置前旧 `playerEpoch` 的消息被忽略。同一 `idempotencyKey` 生成稳定消息编号，重复接收或重试不会重复显示。

聊天使用独立于地图快照边界的分页读取。首次从已确认的最新页面方向回扫，直到收集 50 条有效消息或到达历史边界，并将平台时间/评论 ID 水位、分页方向、尾页和有界待补分片写入缓存。分页严格有序时，以后只读取新增页面及与旧水位重叠的边界页，把新消息合并进已有 50 条窗口；不足 50 条时也不会每次重新扫完整历史。`mixed` 排序时不使用水位提前停止：地图账本仍须每轮全扫有界历史，聊天复用这些页面；两者当前均使用 `MAX_HISTORY_PAGES = 10000` 的分页上限，而非 200 页。因此“保留最新 50 条”是显示与缓存上限，不代表所有情况下只请求 50 条评论。聊天的内存与磁盘消息缓存始终仅保留 50 条，不依赖记录中自报的客户端 `createdAt` 排序，也不会因较新的地图快照覆盖掉聊天历史。

### 4.5 奇珍与素材

公共快照和玩家可见状态包含 `treasureSpawns`、`claimedTreasures` 和 `treasureEpoch`。作者开服时散落默认 240 个普通奇珍；以后通过服主入口提交 `{ "type": "scatter-treasures", "count": 240, "redAscend": 0, "redReroll": 0 }` 重置散落批次，可指定两类稀有赤色素材数量。全部奇珍位于未占领区域；不会在每次客户端同步时自动生成。只有作品作者签名、平台作者来源一致的 `AUTH/type: treasure-scatter` 可以发布刷新结果，随后发布覆盖快照。

玩家抵达奇珍位置后的领取结果通过 `MAP/changes.claimedTreasures` 同步；普通玩家的地图增量不得自行添加刷新点或推进刷新代数。领取记录必须指向已经公布的奇珍 ID、坐标、代数和素材类型。拾取先进入本地待确认奖励，不计入可修炼的素材库存；下一次同步须回读到自己的公开领取记录，并完整覆盖提交前的账本边界、没有未完成分片，再按平台根评论先后确认第一位领取者。确认胜出的奖励只入库一次；较晚的领取直接作废，从而避免先消费素材、后回收时保留已增加的战力。已领取的奇珍不会因后续刷新记录重新出现。

素材数量保存在当前玩家的 `privatePlayers[accountId].materials`，本地覆盖恢复时保留；公共快照不包含 `privatePlayers`。玩家重置时该账号私人素材随其私人状态一起清除。

## 5. 一对一将领书信

```text
GET  /console/api/chats?page=1&limit=500
POST /console/api/chats                    { receive_id }
POST /console/api/chats/messages           { chat_id, content }
GET  /console/api/chats/messages?chat_id={id}&page=1&limit=500
```

发送顺序：

1. 验证发信将领正在身边、处于俘虏区，或与玩家同格部署。
2. 验证收件人是该将领档案中存在过的主公。
3. 用接收方设备加密公钥封装正文，并用发送方签名私钥签名。
4. 先在接收方根评论下写入 `DMWAKE` 回复。
5. 再把 `fyow.direct/3` 密文分片写入双方平台私信会话；分片同样最多重试三次。
6. 接收端验证赛季、发送方签名、封禁状态和频率，再解密放入本地收件箱。

限制为每个发送设备每分钟 12 封、每个发送方每分钟最多接收处理 20 个唤醒。书信正文最多 500 字。前端只显示设定名；账号 ID 仅用于路由、签名验证和服主列表。

## 6. 伴生作品模型

```text
POST /go/api/apps/chat-messages
GET  /go/api/account/point?target={accountId}
```

请求体由 `createModelRequestPayload` 生成，只传固定伴生作品 ID 和：

```text
[[FYOW:TASK:任务名:v1]]
{"schema":"fyow.model-request/1","input":{...}}
```

任务名只负责触发对应世界书，绝不作为会话复用依据。每一条实际发送的消息以及每一次重试都不携带旧会话编号；平台必须返回一个从未使用过的新 `conversationId`。工具完整读取事件流直到结束事件，之后才解析 JSON 并向游戏前端回包。单次请求最长等待 180 秒，同一工具实例的模型请求严格串行。五类任务均在失败时最多使用三个全新会话重试，并校验任务各自的 Schema、长度、枚举、数值范围和禁止占位内容。

每条模型消息发送前后都回读一次平台积分。完成事件附有积分元数据时优先使用其输入、输出和总消耗；节点只提供余额时，以两次平台余额之差作为本次实际消耗，绝不把 token 数量换算成积分。宿主状态通过 `account.points` 暴露当前余额，并在 `modelUsageEvents` 中提供最近 30 条本地记录；每条记录包含任务名、显示名称、重试序号、状态、本次消耗、调用后余额和完成时间。游戏前端顶部常驻显示余额，右侧逐条展示调用记录。

当前五类任务：

- `player.profile-context`
- `general.generate`
- `general.dialogue`
- `general.captive-dialogue`
- `general.memory.update`

普通/俘虏互动的模型输入不包含玩家账号 UUID、将领内部 ID或私信账号目标。历任主公只以设定名和一次性的 `former-lord-N` 路由键出现；模型若返回书信指令，宿主通过本机保存的路由表换回平台账号后发送。回答、书信和压缩记忆中出现账号 UUID，或模型返回越权指令，都会令本次结果失效并在新会话重试。

模型返回只作为结构化内容，不直接决定金币、领地、兵力、时间或战斗结果。初始将领先返回本地预览，玩家可重抽或编辑，确认后才创建玩家；因此预览失败不会产生需要回滚的公共状态。占地奖励将领在公开地图已经提交后进入本地指数退避队列，30 秒起步、最长 15 分钟，保留稳定发现编号避免重试生成两名将领。

## 7. 创作页与迁移

```text
GET  /console/api/installed-apps/{workId}
GET  /console/api/apps/{workId}/model-config/export
POST /console/api/apps/{workId}/model-config
POST /console/api/apps
```

打开卡时从平台回读作品作者并与游戏卡 `companion.authorAccountId` 对照。迁移时导出旧配置、创建新作品、写入配置、再次导出校验摘要、改名旧作品、在新作品写入控制和快照，最后才在旧评论区发布 `RESET`。任一步回读不一致都不会发布重定向。

## 8. 时间与同步

```text
GET /go/api/account/profile
```

工具使用响应 `Date` 头校准时间，以单调时钟推进本地计时；每小时重新校准。评论区静默同步间隔为 5 秒。同步正在执行或玩家行动正在提交时，新一次同步直接合并到下一轮，避免同时覆盖内存状态。

## 9. 本轮缺陷检查结果

已修复：

- 评论接口按旧到新分页却从第 1 页开始读取，旧快照会让全量与后续轮询长期错过真实尾页。
- 同步失败后仍可能使用旧缓存接受玩家行动，造成“界面能操作、平台没有交互”的假运行状态。
- 部署将领互动的内部记忆记录会先发布一次地图增量，外层互动又重复发布相同变更。
- 互动模型可以看到并返回账号 UUID，普通将领也可能返回俘虏专用指令，书信目标缺少本机别名路由校验。
- 回答有效但记忆或书信失败时缺少清晰的原子边界；现在记忆与地图一起提交，书信作为提交后的独立传输报告结果。

- 前端回包没有请求编号，快速操作时可能把结果交给错误按钮。
- iframe 只检查消息标记、未同时检查消息是否来自父窗口。
- 服主确认框取消后没有业务回包，按钮可能永久等待。
- 除入场外的玩家行动没有服务层串行锁，可能与另一行动或后台同步交叉修改。
- 公共评论分片遇到一次临时错误就停止，没有短重试。
- 公开地图已提交、奖励将领生成失败时仍把整次行动报成失败，可能诱导重复行动。
- 公开提交前失败时只有入场会回滚，其余公开行动可能残留在内存。
- 待重试将领若使用新的发现编号，极端崩溃恢复时可能重复生成；现已使用稳定发现编号。

继续观察：

- 平台评论和私信接口的字段、分页与速率规则属于外部依赖，平台改版后需要重新实测。
- 评论区适合秒级到小时级策略同步，不适合即时动作或强实时对战。
- 本地私人数据仍可被本机高级修改者篡改；凡会影响其他玩家的结果必须继续收敛为签名公共地图记录和可验证规则，不能信任对方上传的私人结论。
