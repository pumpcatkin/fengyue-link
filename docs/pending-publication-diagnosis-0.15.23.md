# 0.15.23 待同步行动阻断进入诊断

日期：2026-09-22。

## 证据范围

用户新截图显示 v0.15.22，提示为“行动结果已保存在本机，等待同步，请重试连接”。
它与上一轮的“云端控制记录尚未读取完整”来自不同代码路径。
当前主机没有截图对应测试者的日志，所以原始写入失败究竟来自限流、响应丢失、平台错误或数据校验，应在取得其 Ctrl+Shift+8 导出日志后确认。

## 已重现的问题

1. 进入时云端读取及校验已经成功，但未完成行动补交失败，sync 抛错后 open 也抛错。
2. 界面捕获任意进入错误后返回游戏库并暂停服务。由于轮询在成功 open 后才启动，待同步行动从此只能靠玩家再次进入触发重试。
3. 旧事务只记录行动变化和本地前后状态，没有记录完整签名消息及每段写入确认。长记录在后段失败后重试，会重新发根记录和前面所有片段。
4. POST 的响应丢失不代表平台未收到数据。立即重复发送可能新增重复根记录，仍缺少最后片段，并加重读取和写入负担。

## 修改

- 引入专用 FYOW_PUBLICATION_PENDING 错误，只在进入所需云端数据已通过校验后使用。
- 仅此类待补交错误允许打开经过校验的地图，状态仍为 degraded，继续禁用新的游戏行动。
- 正常启动自动重试和既有退避，手动“重试”按钮也继续有效。失败不删除将领、士兵、行军结果或对话。
- 其他云端读取、控制记录、快照和签名失败仍拒绝进入，不通过忽略校验解决问题。
- 待同步事务保存原签名记录及逐段写入确认，重试保持消息正文及标识不变。
- 每次待同步轮询完整读云端后，按相同作者、相同正文和同一个原生根分支核对已存在的分片，只补交剩余片段。
- 待同步事务 POST 不立即盲重试，模糊结果留到下一轮读取确认。旧事务首次重试也能识别正文相同的既有分片。
- 补交后使用既有事务提交机制恢复一次本地结果，防止重复扣金币、重复结算或重复添加兵力。
- 增加失败码、HTTP 状态、事务号和确认片数日志，保留具体原始错误供后续排查；日志不包含签名记录正文或私有对话。

## 验证

- 39 个测试文件、624 项测试通过。
- 缓存待同步行动重进：云端读取成功、POST 429，返回可展示地图的 degraded 状态并保持轮询；下一轮继续自动重试；网络恢复后变为 ready。
- 恢复前后的金币、行军人数、位置和本地对话一致，再次同步不重发已完成行动。
- 模拟根记录及第 2、第 4 段已被平台接收、但响应丢失，关闭并重建服务后读回，最终只产生一个根分支，每个片段仅写入一次。
- 显式写入失败后只续传剩余片段；v0.15.22 无分片日志的事务也纳入测试。
- 签名被改动的本地待同步记录拒绝发布并继续保留。
- Electron 界面集成验证：带待同步状态进入后不返回游戏库，地图内显示重试按钮；既有重试请求可恢复连接。
- 打包后的 app.asar 桌面集成、登录故障测试、沙箱、安全门、Electron 熔丝、安装包哈希和发布清单签名校验通过。
