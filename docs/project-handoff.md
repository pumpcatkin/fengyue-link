## 《猎艳疆土》当前规则（覆盖下方历史条目）

下列规则以当前 `electron/grid-world-game.cjs` 为准。后文按版本号记录的是当时已经落地的历史状态；其中关于固定 300 将领战力、首修等待 6 小时、1～60 分钟自动连续采集及旧行军费用的描述均已被现行规则取代，不得据此恢复旧行为：

- 地区基础人口在所有位置都使用 100～10000 的同一随机范围，资源等级也使用同一套 D-～S+ 分布；从外围到中心只对最终人口、中立战力、驻军上限和资源产出追加 1 / 1.2 / 1.5 / 2 的内部倍率，界面不单独显示倍率。
- 行军基础耗时为每格 30 秒，基础金币为 `distance * (1 + ceil(soldiers / 10) + carriedGeneralCount * 2)`。全部随行将领计费，只有顺序最前两名提供行军战力与天赋；士兵只能从玩家已确认征集的 `fieldArmySoldiers` 出发。
- 采集是单次 10 分钟任务，每名玩家最多同时采集 3 块领地；完成结算后该格按资源等级进入 D- 1 小时至 S+ 4 小时的真实时间冷却，不自动续采。
- 玩家与将领首次闭关在加入后立即开放，后续仍按 48/168/360/576 小时开放。玩家闭关只消耗金币，不使用素材；将领闭关仍消耗金币和一件素材并更新天赋。
- 所有新生成将领按赛季、账号和生成来源稳定取得 250～350 初始基础战力。攻占中立格与练兵都可能产生待确认的将领候选；确认并接受积分消耗后才进行模型生成。

## 最高优先级维护规则

### 每一次改动都必须更新安装包

这是本项目后续开发的强制规则：

1. 无论改动大小，只要修改了功能、界面、文案、协议、平台控制逻辑、依赖、配置或文档，就必须提升 `package.json` 中的版本号。
2. 同步更新 `package-lock.json` 的版本；右下角初始版本文案也必须与新版本一致。
3. 完成代码修改后必须运行完整测试和构建。
4. 必须重新生成新的 Windows 安装包，不能只更新源码、开发版或 `win-unpacked`。
5. 向用户报告“修改完成”时，必须同时提供本次新生成的 `.exe` 安装包路径和版本号。
6. 新安装包必须继续使用正式版的 `appId` 和 NSIS `guid`，不得改成新的发布身份，否则会破坏覆盖升级与用户数据连续性。
7. 不得把旧版本安装包当作新修改的交付物；安装包文件名中的版本必须与 `package.json` 完全一致。
8. 每次版本更新都必须同步更新桌面上的 `风月联机工具.lnk`，使其目标指向本次最新版本的可执行文件；交付前必须重新解析快捷方式，确认目标存在且 `ProductVersion` 与 `package.json` 完全一致。不得留下仍指向旧安装目录、旧镜像或旧版本可执行文件的桌面入口。

```text
appId: cc.aiero.fengyue.link
NSIS guid: 63340c0b-8899-4ec0-9aa3-5a80da4ed183
```

版本建议遵循语义化版本：

- 小修复、文案和局部 UI：提升补丁号，例如 `0.2.0 → 0.2.1`。
- 新功能或明显行为变化：提升次版本号，例如 `0.2.x → 0.3.0`。
- 不兼容的大版本重构：提升主版本号。

## 一、产品目标与硬性边界

本工具是一个风月/Aiero AI 作品多人联机桌面客户端。用户安装后直接双击打开，在工具中登录账号、选择作品、创建或加入房间、聊天并同步游玩。

核心边界：

- 不使用项目自建的私人服务器后端。
- 联机传输完全借助平台的私人聊天/私信功能。
- 不使用公开聊天室，避免影响普通用户或平台管理员。
- 实际模型调用只发生在房主的作品会话中。
- 访客不能让自己的模型独立生成正式回复，否则会消耗积分且产生不同结果。
- 工具不向普通用户展示完整平台网站；用户只看到工具 UI、作品介绍和经过裁切的对话内容。
- 登录、介绍、对话、私聊等后台页面需要共享同一账号登录态并持续运行。
- 每个工具实例使用独立浏览器分区，可以在同一台电脑上同时登录不同账号。

## 四、整体进程与后台页面架构

每个账号实例对应一个 `AccountBackend`。实例分区为：

```text
persist:fengyue-link-{profileId}
```

同一实例内的后台页面共享该持久化 Chromium 分区，因此 Cookie、登录态、平台本地存储和账号状态保持一致。不同 `profileId` 互相隔离。

### 1. 工具主窗口

`BrowserWindow` 加载 `electron/desktop/index.html`，只显示工具自身 UI。主窗口不直接显示完整平台网站。

### 2. 登录与账号锚点页

隐藏的账号锚点窗口长期保持平台会话在线，承担登录状态检查、账号资料读取和基础 API 环境。

### 3. 作品介绍页

独立的 `WebContentsView`。选择作品后立即准备并保持运行，目标是作品详情中的：

```html
<iframe sandbox="allow-scripts allow-forms allow-pointer-lock">
```

介绍页和对话页彼此独立，开始游玩不会覆盖介绍页。只有更换作品或关闭工具时才销毁对应页面。

### 4. 作品对话页

独立的真实 `WebContentsView`，选择作品后立即加载并在整个作品生命周期中保持运行。非对话模式下把 View 放到窗口外；进入对话模式后，View 与工具内容槽保持完全相同的原生边界，不做裁剪、反向偏移或截图编码。

对话相关的 `loading-game`、`game-empty`、访客等待和访客同步状态都属于对话模式，不能因为平台仍在载入、当前会话为空或同步暂时移开编辑弹窗就退回普通占位页。只有用户主动选择“作品介绍”时才允许介绍 View 覆盖对话 View。必须暂时移开真实对话 View 执行平台编辑时，先发布一张冻结画面作为短暂视觉兜底，完成后恢复同一个真实 View。

平台页面内部不再把尺寸会随作品外壳变化的 `.chat-container` 当成最终捕获框。工具从真实的 `#customized-question-content` 与 `#ai-chat-answer` 消息行求最低共同祖先，把该真实 DOM 祖先提升为固定消息流舞台，并在 CSS 布局层隐藏其路径外分支。没有克隆、截图转码或外观复刻；滚动、命中测试、文本选择、作品内组件和流式绘制仍全部由同一个 Chromium 页面完成。

当前消息行仍以以下节点作为操作锚点：

```text
.relative.flex.items-start.justify-between.gap-3.py-3.px-3
```

不能把 `role="presentation"` 的外层元素当作显示目标。平台的以下原生操作区域会对房主和访客隐藏：

```text
div.MuiStack-root.css-1ajg1ui
```

`<canvas id="game-frame">` 和离屏 `BrowserWindow` 代码只作为紧急回退保留，`liveview.7` 默认不启用。平台不应暴露给玩家的原生消息操作按钮仍由注入 CSS 隐藏。

### 5. 私聊工作页

账号实例保留一个隐藏的常驻账号页面。工具通过平台私信接口轮询并发送带 FYMP/1 前缀的协议消息，不再为每个成员创建额外隐藏工作窗口。

### 6. 临时页面

- 选择作品时可临时显示平台作品选择/浏览窗口；检测到进入作品后立即记录作品并关闭选择窗口。
- Google/Telegram OAuth 使用独立临时登录窗口。
- 联机前置词适配使用独立后台页面打开固定的适配器作品。

## 五、用户界面与登录

### 主页面

- 登录前只能看到登录功能。
- 登录成功后显示横向功能卡片：目前有“联机”和“编辑个人设定”，并预留后续横向卡片空间。
- 标题位于主页右上区域。
- 工具右下角始终显示应用版本号，真实值来自 `app.getVersion()`。

### 域名选择

1. 启动时先显示内置节点、上次成功选择的节点和已有缓存，不等待网络检测完成。
2. 从 `https://aify.pages.dev/` 更新域名目录，并以高并发在后台检测连接状态和延迟；检测失败只作为提示，不阻止用户手动尝试浏览器可打开的节点。
3. 已保存上次节点时立即恢复并在后台预热该节点的中文登录页；首次使用且尚未手动选择时，后台检测完成后自动选中在线节点中延迟最低的一个，但不会自动登录。
4. 用户选择域名并登录后，普通登录页不再允许直接改域名；可从右上角设置中心切换节点，切换会先安全登出当前账号。
5. 邀请链接只传作品后缀；访客使用自己登录时选择的域名拼接后缀。
6. 平台作品列表即使返回其他节点的绝对链接，也只能继承路径、查询参数和片段；所有平台作品页面必须使用当前登录节点重建 URL。

### 登录方式

- 风月账号密码登录。
- Google 登录。
- Telegram 登录。
- 不额外验证 Telegram 身份。
- 可选择“记住密码”。密码通过 Electron `safeStorage` 使用当前 Windows 用户的系统加密能力保存。

登录成功后会自动读取并周期更新：

- 平台用户名；
- 账号等级；
- 当前积分；
- 平台账号 ID。

密码登录只在认证阶段读取账号基础资料；积分、等级等附加资料会并发地在登录成功界面出现后更新，不再阻塞登录返回。认证轮询有明确的 15 秒上限，并在运行日志中记录登录页、提交、认证成功或失败的耗时（不会记录账号密码）。同一个 `profileId` 只允许一个工具主实例运行，防止多个窗口共享同一 Chromium 分区时互相覆盖登录状态；需要多账号时必须使用不同实例名。

应用启动后会显式让默认 Electron 会话和每个账号持久化分区使用 Windows 系统代理设置，并把 Chromium 实际解析出的代理路线写入本次运行日志。作品选择页不设置工具侧加载超时，由 Chromium 按当前节点和代理持续加载。登录后的令牌短暂不可读、页面切换和普通网络失败均视为“不确定状态”，不得切回登录页；只有账号资料接口持续明确返回 401/403，经过多次、跨时间窗口确认后才允许判定会话失效。活动作品或房间存在时，即便持续拒绝也保留当前登录与对话视图，等待网络/节点恢复或用户显式登出，不允许跳转登录页破坏会话。显式登出不受该防抖影响。

账号未达到 2 级时，创建和加入房间按钮不可用。

## 七、作品、会话和模型

### 作品选择

- 创建房间前房主必须先选择作品。
- 选择完成后立即准备介绍页和对话页，并在后台读取会话列表和模型列表。
- 房间存在期间，房主和访客都不能更换作品。
- 关闭/退出房间后恢复选择作品功能。

### 平台会话

工具中的统一名称是“会话”，不要再称为“存档”。

- 可读取平台当前作品的会话列表。
- 房主可在开房前选择已有会话。
- 房主可在开房前新建会话。
- 房间开启期间禁用新建和切换会话。
- 会话锚定使用平台不可见的会话 UUID/稳定键，不依赖可手动修改的会话名称。

访客不复制房主历史：

- 房主切换或新建会话时，每位访客应对应一个自己的平台会话。
- 若本地已有房主会话到访客会话的锚点，则恢复该会话。
- 若没有锚点，则为访客建立一个新的空白会话。
- 后续只同步加入之后的新回合记录。

### 模型列表

- 房主读取平台实际模型列表。
- 工具显示模型名称、系列、价格系数、出字/成功率和平台提供的延迟信息。
- 可按 Gemini、Claude、DeepSeek、GPT、Grok、Kimi、Qwen、Other 等系列筛选。
- 房主点击模型卡片后立即切换，不再使用额外“应用模型”按钮。
- 房主当前模型同步给所有成员显示。
- 访客加入时只需保证自己的后台选择是平台仍存在的有效模型；无效时自动换成列表中可用模型。

## 八、创建房间和加入房间

### 创建房间

1. 房主选择作品；工具默认建立新的空白平台会话，也可从保留的会话列表手动切换旧会话。
2. 输入房间密码。
3. 工具使用平台“简易创作”生成一个私人作品作为邀请入口；不能使用高级创作。
4. 工具显示“您的邀请链接”，实际传递的是 `/zh/explore/installed/{id}` 后缀。
5. 私人作品虽不公开，但知道链接的访客可以打开作品详情、通过作者头像找到房主主页并建立私聊。

### 加入房间

1. 访客填写房主的邀请链接后缀和房间密码。
2. 工具拼接访客当前登录域名。
3. 打开私人作品详情并识别作者账号 ID、用户名和私聊入口。
4. 自动创建或复用访客与房主的私人聊天。
5. 通过私聊完成密码证明和加入认证，无需房主手动批准。

### 密码认证

协议不在私信中发送明文密码：

```text
hello → challenge → join-proof → join-accept
```

房间密码先与房主身份派生 verifier，再对房间号、随机 challenge 和玩家资料生成证明。错误密码、重名、过期邀请、已被移出的成员和游戏已经锁定都会收到明确错误。

## 九、FYMP/1 私信协议

协议正文以如下前缀开始：

```text
§FYMP1§
```

后方是 Base64URL 编码的 JSON。基础信封字段：

```json
{
  "v": 1,
  "id": "全局唯一消息 ID",
  "roomId": "房间 ID",
  "type": "消息类型",
  "from": "发送账号 ID",
  "seq": 1,
  "ts": 1780000000000,
  "payload": {}
}
```

实际桌面端主要消息类型包括：

- 加入：`hello`、`challenge`、`join-proof`、`join-accept`、`error`。
- 成员：`members-sync`、`member-joined`、`member-removed`。
- 会话：`conversation-anchor`、`anchor-ready`。
- 回合：`turn-submit`、`turn-state`、`round-input`、`round-input-ack`、`round-result`、`round-result-ack`。
- 房间聊天：`room-chat-submit`、`room-chat-append`、`room-chat-sync-request`、`room-chat-sync`。
- 模型：`model-sync`。
- 插件：`plugin-settings-sync`；权威运行结果随 `round-input` / `round-result` 传输。
- 回复操作：`message-operation`、`message-operation-ack`。
- 长消息：`chunk`。
- 连接维护：`ping`、`pong`。

长文本使用 gzip 压缩、Base64URL 和分片传输。接收端按 `transferId`、分片索引和总数重组，全部到齐后再解压。协议按消息 ID 去重，并在重要发送/同步阶段重试，以抵抗私信延迟和网络波动。

## 十、成员、房间聊天和提醒

### 成员列表

- 显示平台名、游戏内设定名、基础设定、外观设定及两类设定字数。
- 显示本轮是否确认、访客会话是否准备完成。
- 新成员加入时，房间中原有成员会在右上角看到短暂提示并听到提示音。
- 房主可将访客移出房间。
- 移出只允许在安全的回合收集阶段执行；模型生成、已有成员提交、提示词同步或记录操作进行中时暂时禁用。
- 被移出的成员会收到通知并离开房间，本次房间不能用相同账号立即重新加入。
- 权威成员名单带 `rosterRevision`，访客忽略旧版本名单。
- 移出成员后，房主会立即重新写入当前会话的多人提示词，删除该成员的人设标签；若平台写入暂时失败，下一轮发送前会再次校验和重试。

### 房间聊天

- 所有访客只把聊天消息发给房主。
- 访客发送后立即按本地发送时间显示一条乐观消息，并保留稳定 `clientMessageId`；无需等待房主广播才能看见自己的内容。乐观消息只存在于本地展示状态，不进入权威消息快照。
- 房主回传同一 `clientMessageId` 的正式消息后，访客用正式消息替换乐观消息，不得重复显示；随后必须重新使用房主回传的 `sentAt`、`sentAtIso` 和稳定消息 ID 排序，因此权威同步仍可改变消息在记录中的位置。
- 房主按发送时的真实 Unix 毫秒时间戳排序，再将每条新增消息广播给所有成员。
- 同一毫秒时使用稳定消息 ID 作为确定性次级排序，不依赖客户端自增编号。
- 正常情况下只广播新增消息，不频繁发送完整聊天列表。
- 检测到修订号缺口、新成员首次加入或网络恢复时，访客请求完整压缩快照。

## 十一、多人回合与对话同步

这是最重要的业务链路。

### 1. 收集输入

- 所有成员在工具底部输入文本并点击确认。
- 访客通过私信向房主发送 `turn-submit`。
- 房主保存自己的输入和访客输入，并广播 `turn-state`。
- 工具显示哪些设定名已经确认、哪些仍在等待。
- 发送给作品模型的聚合内容只使用玩家设定名，不包含平台数字账号 ID。

### 2. 房主调用模型

- 收齐全员输入后锁定本轮成员名单。
- 房主先验证多人会话提示词已经正确写入。
- 房主将结构化的多人输入写入自己的平台作品会话。
- 聚合输入使用合法 JSON：顶层固定为 `Users` 数组，每项只包含 `user-name`（设定名）与 `input`（该玩家本轮原文）。
- 只有房主等待模型流式生成和最终完成。
- 工具实时捕获房主后台平台对话，因此输入出现和 AI 流式输出时都应在“对话界面”中可见。

### 3. 访客先建立空回复位置

房主开始生成时会广播 `round-input`。访客收到后必须：

1. 打开已锚定的对应作品会话；若不存在则先创建空白会话并完成锚定。
2. 向平台发送与房主相同的聚合输入内容。
3. 逐块读取原生响应，取得真实 task_id 后立即调用平台“终止输出”接口，等待停止确认和流结束，避免访客模型生成长回复。
4. 保留平台产生的空 AI 回复位置。
5. 回传 `round-input-ack`，然后等待房主完整输出。

访客在此阶段的工具页面仍显示先前上下文，并提示等待房主，不显示自己的流式模型输出。

必须先取得真实任务编号再停止，不能把按钮恢复或本地连接中断当作服务端已经终止。原生停止按钮可能在 task_id 尚未到达时就隐藏自己，此时服务端仍生成。停止确认之后等待响应流结束，再清除残留前端忙碌状态。若模型已自然完成，现有回复只能作为可编辑占位，`round-result` 仍必须用房主输出覆盖它。按用户最新要求，加入房间和每轮发送前强制验证实测访客模型；仅修改该访客作品默认与会话模型配置，不改变房主模型、提示词或记忆。测试中即使正文和 token 为零也仍记 2 积分。

### 4. 同步房主结果

房主生成完毕后读取：

- 本轮聚合输入；
- 完整 AI 输出原文；
- 模型名称；
- 输入积分；
- 输出积分；
- 总积分；
- 完成时间。

这些内容通过压缩分片 `round-result` 发送给访客。访客收到完整结果后：

1. 找到刚才终止生成产生的空 AI 回复。
2. 使用平台原生“编辑”能力写入房主完整输出。
3. 保存编辑。
4. 重新读取平台会话，验证输入和输出都存在且一致。
5. 成功后发送 `round-result-ack`。

失败时保留当前步骤并重试，当前主要同步步骤最多重试 4 次。只有成功或达到重试上限后才结束该同步任务。

`round-result` 的活动实现必须是严格的“只编辑”路径：先通过平台消息接口确认当前锚定会话已经存在与房主完全一致的本轮输入，再编辑 `round-input` 阶段留下的空回复。该阶段不得再次点击发送、不得再次调用终止输出；状态丢失时宁可返回错误并重试验证，也不能创建重复回合。

### 5. 下一轮

- 房主收到全部访客成功回执后开放下一轮。
- 第 2、3、更多轮继续复用同一会话锚点。
- 新结果到达后，“对话界面”按钮会动态高亮：房主在平台输出完成时高亮，访客在本地平台记录同步完成后高亮。

## 十二、回复刷新、编辑和删除

房主对最近一轮拥有工具内的：

- 刷新；
- 编辑；
- 删除。

操作必须等效于平台原生操作，并通过 `message-operation` 同步到所有访客。访客在自己的锚定会话中执行相同操作并返回 `message-operation-ack`。操作进行中会锁定不安全的成员/回合操作。

房主编辑不再弹出会被原生 `WebContentsView` 覆盖的全窗口工具弹窗。编辑按钮会在联机侧栏展开工具自己的文本框；保存后主进程暂时移出真实 View，通过脚本打开最近一条平台回复的原生编辑器、写入完整文本、保存，并重新读取平台消息接口校验内容一致后才同步访客。

## 十三、多人会话提示词

平台会话配置字段：

| 页面字段 | API 字段 | 当前用途 |
| --- | --- | --- |
| 提示词 | `pre_prompt` | 保存多名真人玩家的人设。 |
| 前置词 | `pre_text` | 保存通用多人回复规则和作品专属格式片段。 |
| 后置词 | `post_text` | 当前不修改。 |

配置保存使用 `/go/api/apps/config`，必须携带当前 `app_id`、当前真实 `conversation_id` 和 `is_global: false`，只修改当前会话，不修改作品全局配置。

### 人设注入

- 保留用户原有提示词。
- 在字段末尾维护唯一受控标签。
- 再次进入或成员变化时先删除旧受控标签再写入，不重复追加。
- 标签说明其中是多名不同真人用户，模型不得主动扮演、代替或决定这些角色。
- 姓名、基础设定和外观设定经过 XML 转义。

### 通用前置词

- 回复最前方列出当前参与用户设定名。
- 按设定名区分每位真人本轮输入。
- 不代替真人补写言行、心理或决定。
- 作品已有状态栏时，为每位在场用户分别生成所需用户状态节点。
- 公共世界/NPC 状态只保留一份。
- 作品没有状态栏时不强行制造破坏格式的新状态栏。

### 联机前置词适配

- 选择作品后、开房前可一键适配。
- 会消耗少量积分。
- 最多读取该作品 5 个合格旧会话样本。
- 每个样本只取最后一段非空 AI 回复。
- 含 `Google's Generative` 使用政策标记的回复被排除。
- 使用固定作品 `649fbb98-07b3-4cbd-a7ed-3e3d224dca87` 分析。
- 每次适配先为适配器建立纯净新会话，再发送正常换行、以代码块包裹的样本，不发送转义未还原的 JSON 原文本。
- 适配器只返回简短的作品格式差异建议，不返回 JSON，不重复通用规则。
- 有效结果按目标作品 `app_id` 永久保存；再次适配覆盖旧结果。
- 房间使用时固定组合“通用前置词 + 作品专属片段”，组合本身不再调用模型。

完整细节见：

- `docs/multiplayer-prompt-injection.md`
- `docs/status-adapter-generator-prompt.md`

## 十五、本地持久化

以下文件位于 Electron `app.getPath("userData")`，不在安装目录中：

| 路径 | 内容 |
| --- | --- |
| `credentials/{profileId}.json` | Windows `safeStorage` 加密的账号密码。 |
| `node-selections/{profileId}.json` | 最近一次选择的登录节点，用于下次启动立即恢复和预热。 |
| `instance-locks/{profileId}.lock` | 当前同名实例的进程锁；正常退出时删除，异常退出后的陈旧锁会自动回收。 |
| `character-profiles/{profileId}.json` | 多角色设定与当前选中角色。 |
| `save-anchors/{profileId}.json` | 房主会话与访客对应会话的 UUID 锚点。 |
| `multiplayer-prefix-adapters.json` | 按作品 ID 保存的专属适配前置词。 |
| `plugin-settings/{profileId}.json` | 房主本机的插件启用状态、顺序与效果判定设置。 |
| `session-logs/{profileId}-{pid}.jsonl` | 脱敏的当前进程临时日志；正常关闭时删除，异常遗留受保留上限控制。 |

除进程锁和临时日志外，JSON 状态通过同目录临时文件原子替换，并在 `.bak` 中保留上一份有效内容；主文件解析失败时尝试备份。Chromium 登录态、Cookie、本地存储等保存在对应持久化 partition 中。

镜像安装器配置 `deleteAppDataOnUninstall: true`，卸载时会清理镜像专属用户数据目录；正式替换安装器配置为 `false`，避免卸载正式版时误删需要保留的账号与本地状态。两个通道的产品名、appId、GUID、快捷方式和输出目录不得交叉修改，详见 `docs/release-channels.md`。

- 右下角固定显示 `v{app.getVersion()}`。

### WebContentsView 消息流舞台

- 原生 View 始终与工具内容槽同尺寸，不使用父 View 裁剪、子 View 负偏移、离屏截图或低帧率画布。可见位置和 Chromium 命中位置天然一致。
- 每次隔离刷新从 `#customized-question-content`、`#ai-chat-answer` 及工具卡片的真实消息行计算最低共同祖先。这个现有 DOM 节点成为滚动舞台，平台 React 节点不会被克隆或搬出事件根。
- 舞台到页面根部之间的布局盒使用 `display: contents` 消除作品之间不同的侧栏宽度、定位包含块、裁剪和粘性外壳；路径外分支隐藏且不参与命中。消息行内部完全保留平台的原生 HTML/CSS/事件，因此世界信息、记忆归档及作品自定义组件都能正常交互。
- 不再扫描或禁用回复内部的透明层、Canvas、SVG、自定义标签或伪元素。作品输出内部的命中规则属于作品本身，工具只隔离消息流外部的平台壳。
- 切换历史会话时，平台外壳会先完成加载、随后异步注入消息。若用户当前正在查看对话界面，工具必须保持“正在载入”并等待真实消息节点；后续探测到消息时要从 `game-empty` 自动提升为 `game`，不能让已捕获的帧继续被空会话占位层遮住。
- 执行平台原生编辑/保存时必须暂时把真实 View 移出可见区域，并同时移除 `gamePrivacyCssKey` 和旧的隔离 CSS；编辑完成后重新应用聊天区隐私 CSS 再恢复显示。平台编辑对话框位于 `.chat-container` 外部，不能在全局隐藏 CSS 生效时查找它。
- 早期手动 Shadow DOM 实验卡片代码仍作为内部诊断能力保留，但不再出现在普通 UI；正式插件入口位于联机栏顶部“插件”页。
- 正式插件卡片使用房主权威 `runId`、回合号、阶段、状态和积分数据，并通过现有压缩分片回合包同步，避免另建不兼容的卡片传输链路。
- 输入处理栈卡片优先锚定与本轮完整聚合输入原文或去空白原文匹配的 `#customized-question-content`；平台对 JSON 做显示重排时允许包含关系匹配。注入开始后会先短暂等待新输入节点，仍无法匹配时才使用最新输入作为兼容锚点。多个卡片按 `order` 和插件 ID 排序，并以幂等恢复函数防止平台 React 重绘或隔离观察器形成重复移动循环。

### 当前配置

```text
产品名：风月联机工具
版本：0.14.21（模型积分逐次结算与新会话硬约束）
平台：Windows x64
格式：NSIS 安装程序
Electron：44.0.0
输出目录：release
安装方式：当前 Windows 用户，可选择安装目录，不要求全局安装
卸载程序：安装目录内保留 `Uninstall 风月联机工具.exe`
```

当前安装包：

```text
release/fengyue-link-0.14.21-setup.exe
```

`win-unpacked` 只用于冒烟测试，不是发给普通用户的正式更新文件。

### 标准打包命令

```powershell
npm run pack:win
```

它会先运行 Vite/TypeScript 构建，再生成 NSIS x64 安装程序、`latest.yml` 和 blockmap。正式安装包内置 Electron/Node.js 运行时，普通用户无需预装 Node.js；Node.js/npm 只用于源码开发和打包。

默认构建已经是正式版身份，不再存在第二套镜像晋升命令。生成安装包本身不会修改已安装程序；运行安装包后会覆盖升级正式版并继续使用正式用户数据。

如果 Electron 官方下载在当前网络超时，可以把经过官方 SHA-256 校验的 Electron ZIP 放入一个本地目录，再使用：

```powershell
npx electron-builder --win nsis --x64 --config.electronDist=release-cache
```

本地 ZIP 文件名必须保持：

```text
electron-v{electronVersion}-win32-x64.zip
```

不得使用未校验的运行时。当前 Electron 44.0.0 Windows x64 ZIP 的官方校验值仅适用于该精确版本；升级 Electron 后必须重新取得新版本官方校验值。

### 每次交付检查清单

1. 提升 `package.json` 版本。
2. 同步 `package-lock.json`。
3. 同步 `electron/desktop/index.html` 中版本号的初始显示值。
4. 确认 `electronVersion` 处于没有已知高危漏洞的受支持版本。
5. 运行 `node --check`、`npm test`、`npm run build`。
6. 运行 `npm run pack:win`。
7. 检查 `release/win-unpacked/version` 是目标 Electron 版本。
8. 检查安装程序的 `ProductVersion` 是本次应用版本。
9. 启动 `release/win-unpacked/风月联机工具.exe` 做冒烟测试，再正常关闭。
10. 计算安装程序 SHA-256。
11. 使用项目目录外的 Ed25519 私钥生成并复核 `release/github` 下的签名发布清单。
12. GitHub Release 的标签、安装包、blockmap、`latest.yml`、清单和签名必须属于同一版本且保持字节不变。
13. 更新桌面 `风月联机工具.lnk`，重新读取其目标并确认目标文件存在、`ProductVersion` 与本次版本一致。
14. 向用户提供新的 `.exe`，不能只提供源码。

安装器会创建正式版桌面和开始菜单快捷方式。用户运行更高版本、相同正式版 `appId` 和 `guid` 的安装包即可覆盖升级，并继续使用现有正式用户数据。无论快捷方式由安装器覆盖还是维护者手动更新，都必须执行上述目标与版本复核，不能仅凭快捷方式名称判断它已经更新。

### 当前发布限制

当前安装程序尚未使用商业代码签名证书，因此 Windows SmartScreen 可能在第一次运行时提示未知发布者。内部测试可以继续运行；正式面向大量用户公开分发前，应购买代码签名证书并把签名加入构建流程。不要用临时自签名证书冒充正式发布签名。

## 十九、已知脆弱点与修改注意事项

1. 平台 DOM 类名、MUI 结构、接口字段或会话本地状态可能随平台更新改变。出现会话读取、按钮点击、模型列表或画面为空时，应先检查真实后台页面和网络接口，不要盲目增加固定等待时间。
2. 对话页必须在选择作品后立即后台挂载并清空平台当前会话状态，默认建立新会话；不能改回点击“对话界面”按钮时才创建。
3. 介绍页、对话页和私聊页在作品/房间生命周期内必须同时保持运行。
4. 不能让访客在 `round-input` 阶段正常等待自己的模型完成；必须发送后立即终止。
5. 不能把访客历史同步恢复成“复制房主全部历史”。当前设计是新建/恢复访客自己的锚定会话，只同步新回合。
6. 会话锚定不能使用“新的对话-1”等名称，因为名称可修改。
7. 不得把平台数字账号 ID 发送进作品模型输入；模型侧只使用设定名和对应文本。
8. 私信协议可以包含账号 ID 用于路由和认证，但模型聚合提示不包含这些 ID。
9. 不要把公开聊天室重新引入联机传输。
10. 不要让房主移出操作在本轮已经有人提交、正在生成或正在同步时执行。
11. 修改成员资料/名单后必须同步更新会话提示词受控标签。
12. 更换 Electron 主版本后要重新测试隐藏窗口、offscreen/capture、输入事件、`safeStorage` 和 NSIS 安装。
13. `src/app.ts` 是遗留浏览器脚本，不代表桌面端最终行为。桌面功能修改必须检查 `electron/main.cjs`、`preload.cjs` 和 `electron/desktop/*`。

## 二十、建议新对话的第一步

插件专项新对话只需先完整阅读 `docs/plugin-authoring-guide.md`，再按其中的最小代码索引定位实现；不要同时全文加载本交接文档和所有插件专题文档。

跨模块或非插件的新开发对话应先阅读：

1. 本文件 `docs/project-handoff.md`；
2. `docs/multiplayer-prompt-injection.md`；
3. 与当前任务直接相关的 Electron 代码；
4. `package.json` 的当前版本和安装配置；
5. 最近一次 `release` 安装包版本。

新对话应明确遵守：**任何改动完成后都必须提升版本并重新生成新的 Windows 安装包。**
