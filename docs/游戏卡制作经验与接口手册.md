# 游戏卡制作经验与接口手册

核对日期：2026-09-26
性质：基于当前仓库的实现记录，供下一次对话设计“模型生成游戏卡”的编辑器使用。本文不代表已经实现通用游戏卡 SDK，也不要求更新客户端或平台作品。

## 一页理解：三个发布面不是一回事

制作和发布游戏卡时要把下面三条链路分开理解：

| 发布面 | 作用 | 玩家何时获得更新 |
| --- | --- | --- |
| 本地游戏卡 JSON | 保存作品绑定、配置快照、程序摘要和路由身份；用于导入、校验和离线恢复 | 玩家导入/安装包含新 JSON 的工具后 |
| 伴生作品平台配置 | 保存作品详细介绍、前置词、提示词、后置词和世界书；详细介绍中的程序信封是云端程序入口 | 玩家打开游戏时读取当前作品，老客户端只要理解同一协议即可即时获得 |
| GitHub 工具 Release | 更新桌面宿主、IPC、同步队列、规则引擎和游戏库文件 | 玩家点击“重启并安装”或手动安装新客户端后 |

因此，“上传 GitHub”不会自动修改伴生作品，“更新伴生作品详细介绍”也不会替换桌面宿主。只改世界书和模型提示词通常走平台配置；改宿主接口、权限、同步、规则或沙箱时必须发布新客户端。每次发布都要分别记录三者的版本、摘要和回读结果。

## 世界书调用方式（当前实现）

世界书是平台模型请求的**按关键词注入规则**，不是游戏卡 JavaScript，也不是一个可由玩家直接调用的 API。宿主先按任务构造一条带机器标记的请求，再由平台把匹配的世界书条目注入模型上下文：

```text
[[FYOW:TASK:general.dialogue:v1]]
{"schema":"fyow.model-request/1","input":{"schema":"具体任务输入/1", "...":"..."}}
```

调用顺序是：

1. 游戏宿主选择已登记任务，并生成唯一任务标记和结构化输入；游戏卡前端只提交意图，不直接访问模型、Token 或平台 HTTP。
2. 平台创作配置先应用全局 `pre_text`、`pre_prompt`，再按 `world_book[].key` 匹配条目；当前条目使用 `_or_[[FYOW:TASK:任务名:v1]]`，导出后的 `key_region` 为 `2`，`enable=true`、`probability=100`。
3. 世界书的 `value` 给出任务约束和输出 Schema；模型返回后，宿主解析 JSON、检查字段/长度/枚举和任务权限，失败才进入重试或人工确认流程。
4. `post_text` 再约束最终输出；宿主把通过校验的结果写入游戏状态和本地/云端记录。

编辑器生成新任务时，必须同时登记宿主任务白名单、输入/输出校验、计费和重试语义；仅新增一个关键词不会让现有服务自动支持新任务。全局提示词放作品的共同约束，任务细节放对应世界书，避免把游戏规则、账号标识或平台接口写进模型可自由改写的文本。

### 世界书上传与验证

平台上传不是“点击保存按钮就算完成”。正确流程是：

1. 从当前作品导出配置，保留完整原始快照；不要用手写别名覆盖平台字段。
2. 归一化作品名称、简介、详细介绍、三段提示词和世界书数组；`app.description` 放程序信封，世界书逐项保留 `group/key/key_region/value/enable/probability/sort/depth`。
3. 提交创作页保存请求，等待最终确认对话框完成，再调用导出接口回读。
4. 逐项比较回读值，至少核对程序 `gameId`、宿主 API 版本、程序 SHA-256、世界书数量、触发键、`key_region=2`、启用状态和概率；回读不一致就判定上传未完成。
5. 把回读配置写进对应 JSON 卡，重新计算配置摘要和整包摘要；不要把本地 JSON 的存在误判成全服已更新。

平台字段可能轮换别名，程序必须先归一化再保存。当前服务使用 `/console/api/apps/{workId}/model-config` 保存、`/console/api/apps/{workId}/model-config/export` 回读；这些是宿主内部接口，不能暴露给游戏卡代码。

## 0. 先读：现状与目标

当前已实现的是 `fyow.game-card/1`、`fyow.program/1` 和 `fyow-host/1`。运行实例是《猎艳疆土》：卡片承担界面和输入，游戏规则、同步、评论、模型任务与平台访问由宿主中的专用引擎承担。**能导入一张格式正确的 JSON，不等于新玩法可仅靠 JSON 在当前宿主运行**；新游戏的行动类型并不会自动获得通用存档、评论、模型调用接口。

此前的 [游戏卡接口规范化与创作助手方案.md](游戏卡接口规范化与创作助手方案.md) 描述 `/2` 协议和编辑器方向，**它是设计稿，不是现有 API**。后续模型生成编辑器应先解决通用宿主能力与隔离，再让模型按机器可校验的格式产出代码和提示词；不要让模型假定现有《猎艳疆土》的私有协议就是所有游戏的公共 SDK。

## 1. 系统组成与数据流

```text
游戏卡 JSON：身份、伴生作品绑定、配置快照、程序摘要
  -> 工具导入校验 -> 本地游戏库（卡 ID + 作品 ID 区分实例）
  -> 打开作品，读作品“详细介绍”的有效程序包 -> 沙箱 iframe 执行界面
  -> postMessage 给受信桌面页 -> IPC -> 主进程 OnlineWorldService
  -> 账号、规则、模型、评论/私信、同步和持久化由宿主处理
  -> 状态/结果/错误返回 iframe
```

平台作品的“详细介绍”是当前程序包的云端入口。打开时宿主会校验线上程序和 `gameId`，优先使用有效的线上详细介绍；本地卡中的程序是经验证的快照/后备，不是无条件覆盖云端。同步未完成或连接降级时，可能展示已有状态，但涉及写入的行动受限。卡版本号、程序摘要、客户端版本和服务器赛季是不同概念，不能混为一个“版本”。

伴生作品还存放作品创作配置：系统前后置提示词及世界书；作品评论/回复承载本局公共记录，私信承载定向消息。玩家本地保存账号隔离的私有状态与待上传操作。服务器搬迁换新的作品与赛季，旧 JSON 不能作为唯一寻址依据；宿主读取原作品的迁移指令并追随新作品。

## 2. 当前 JSON 卡包接口

以下是结构示意，**不是可直接导入的文件**；真实摘要必须由仓库工具生成，不能手填：

```json
{
  "schema": "fyow.game-card/1",
  "cardId": "cc.example.my-game",
  "gameId": "cc.example.my-game",
  "title": "游戏名称",
  "version": 1,
  "companion": {
    "origin": "https://PLATFORM_ORIGIN",
    "workId": "WORK_ID",
    "authorAccountId": "AUTHOR_ACCOUNT_ID",
    "name": "作品名称",
    "summary": "作品简介",
    "language": "zh-Hans",
    "installedUrl": "https://PLATFORM_ORIGIN/zh/explore/installed/WORK_ID",
    "configurationUrl": "https://PLATFORM_ORIGIN/zh/app/WORK_ID/configuration",
    "configuration": {
      "app": {"id": "WORK_ID", "name": "作品名称", "description": "[[FYOW-PROGRAM/1:...]]", "summary": "作品简介", "language": "zh-Hans"},
      "pre_text": "...",
      "pre_prompt": "...",
      "post_text": "...",
      "world_book": []
    },
    "configurationSha256": "64位十六进制摘要"
  },
  "program": {"format": "fyow.program/1", "apiVersion": 1, "digest": "64位十六进制摘要"},
  "exportedAt": null,
  "packageSha256": "64位十六进制摘要"
}
```

`cardId`/`gameId` 有字符和长度校验；作品来源必须 HTTPS，作品 ID 与作者账号 ID 必须有效；`configuration.app.id` 与绑定作品一致。校验依次核对规范化配置 SHA-256、详细介绍程序的 SHA-256、`gameId`/宿主 API 版本和整包 SHA-256。单个 JSON 文件上限 8 MiB。库键是 `cardId::workId`，所以同一游戏的不同作品实例互不覆盖。`version` 是整数卡修订，用于本地游戏库比较；`exportedAt` 参与同版本的新旧判定。

配置导出存在平台字段别名。读入时统一通过 `normalizeConfiguration()`，例如作品名称的 `name/nm/ttl/title/app_name`，详细介绍的 `desc/descr/dsc/intro/description`，世界书的 `world_book/wbook/lore_bk/world_bk/wb`。**生成或编辑平台配置时须先归一化，再从实际导出回读校验**，不要通过字符串替换原始 JSON 猜测字段。修改配置后要重新计算配置摘要与整包摘要。

相关函数：`builtInGridProgram()`、`createBundledGridCard()`、`validateGameCard()`、`normalizeConfiguration()`、`createExportedGameCard()`、`rebindGameCard()`、`refreshGameCardProgram()`、`gameCardLibraryKey()`，见 `electron/online-world-card.cjs`。这些是 Node 主进程内部函数，不是 iframe 可调用的接口。

### 程序包

`packProgram({gameId,title,html,apiVersion:1})` 将包含完整 HTML/CSS/JS 的 manifest 做规范 JSON、gzip、SHA-256 和 base64url 编码，形成：

```text
[[FYOW-PROGRAM/1:<压缩数据的 SHA-256>:<base64url 压缩数据>]]
```

详细介绍可含其他文字，但必须含有效信封。解压 HTML 不超过 1 MiB，压缩内容不超过 256 KiB。`parseProgram(description,expectedGameId)` 检查摘要、格式、版本与游戏 ID；`injectSandboxCsp()` 注入限制资源与网络的 CSP。当前不接受外链脚本或外链样式，使用单文件 HTML（内联 CSS/JS）；`composeSingleFileProgram()` 是内置卡的组合工具。运行 iframe 使用 `sandbox="allow-scripts"`，卡片代码不得把 `fetch`、直接平台 API、文件系统或 Electron IPC 当作可用能力。

## 3. 作品和世界书的制作

1. 确定作品 ID、作者账号 ID、`gameId` 与 `cardId`；新服务器使用独立作品 ID。作品作者身份由平台验证，不由 JSON 中的自称决定。
2. 编写游戏 HTML/CSS/JS 与清晰的数据模型；把跨设备状态、权限和结算规则归到宿主/协议一侧。当前新玩法尚需新增通用宿主或专用适配器。
3. 设计模型任务：每项有唯一任务标识、输入 schema、输出 schema、字数/范围/枚举、失败重试与计费提示。作品全局 `pre_text`、`pre_prompt`、`post_text` 只写共同约束；任务具体要求放对应世界书。
4. 每个世界书条目定义 `group`、`match_type`、`key`、`key_region`、`value_type`、`value`、`value_configs`、`value_region`、`sort`、`depth`、`probability`、`enable`。当前内置任务以 `_or_[[FYOW:TASK:<任务名>:v1]]` 为触发键、`key_region:2`、`enable:true`、`probability:100`；不要把这些猎艳疆土专用键名误当通用平台规则。
5. 把程序信封放入创作配置的 `app.description`，保存配置后重新导出并核对程序、提示词和世界书。平台编辑页还需要确认保存是否完成，不能只以按钮点击成功作发布证明。
6. 生成与作品绑定的卡包，执行 `validateGameCard()`；先离线测试，再用测试作品和测试账号试运行，最后由作者发布正式作品。写入云端后再次导出回读比对，避免前端显示与实际配置不同。

当前猎艳疆土只开放七个固定模型任务，输入格式是：

```text
[[FYOW:TASK:general.generate:v1]]
{"schema":"fyow.model-request/1","input":{"schema":"具体任务输入/1", "...":"..."}}
```

任务列表与职责：

| 任务名 | 用途 / 典型返回 |
| --- | --- |
| `player.profile-context` | 补全玩家角色上下文：`personaSummary`、`appearanceSummary`、`speechStyle`、`relationshipApproach` |
| `general.generate` | 新将领：姓名、性别、体格、外观设定、核心设定；战力由游戏规则分配，不信模型数值 |
| `general.dialogue` | 普通将领答复、可空旁白、可选写信/外观指令、压缩记忆 |
| `general.captive-dialogue` | 俘虏答复，另可返回归顺指令 |
| `general.memory.update` | 长期记忆摘要与亲密度变化，压缩概述上限 150 字符 |
| `general.letter` | 在受限收件人集合内生成书信正文 |
| `general.appearance-edit` | 按变更说明修改完整外观设定 |

模型请求由宿主通过平台聊天消息接口发起、流式读取并校验结构化结果；卡片本身不能任意访问模型。新任务不是在世界书加个关键词就会自动被现有服务承认，还必须扩展主进程任务白名单、输入输出校验和计费流程。七项条目的当前原文在 `electron/online-world-card.cjs` 的 `GRID_COMPANION_COPY.worldBook`。

## 4. 运行时通信：iframe 到宿主

卡片发送 `parent.postMessage()`，桌面页验证来源是当前游戏 iframe、固定 `source`/`protocol`、消息类型、长度（不超过 128 KiB）；需要回复的请求必须有 UUID `requestId`。

```js
parent.postMessage({
  source: "fyow-grid-conquest",
  protocol: "fyow-host/1",
  type: "intent",
  requestId: crypto.randomUUID(),
  intent: {type: "start-mining", x: 10, y: 20, idempotencyKey: crypto.randomUUID()}
}, "*");
```

宿主回包以 `source:"fengyue-host"`、`protocol:"fyow-host/1"` 标识，`state` 是异步状态更新，`result` 有 `result` 和原 `requestId`，`error` 有 `message`、`errorCode`、`retryable` 等。卡片须核对 `event.source === parent`、来源标记与协议，用 `requestId` 对应并结束按钮等待状态；不能把一次超时直接等同于云端未提交。当前 `game.js` 的 `host()`、`sendIntent()`、回包监听是参考实现。**现有 `source` 和意图路由仍绑定猎艳疆土，新游戏不能靠复制这个标记绕过专用规则。**

| `type` | 请求数据 | 行为 / 权限 |
| --- | --- | --- |
| `ready` | 无 | iframe 加载后请求当前状态，宿主推 `state` |
| `sound` | `volume`、`revision` | 本机音量设置，回 `sound`；不走游戏规则 |
| `library` | 无 | 返回游戏库，关闭游戏页面 |
| `intent` | `intent` 对象 | 提交/查询当前游戏行动；宿主返回 `result` 或 `error`，可能再推 `state` |
| `sync`、`reconnect` | 无 | 重新连接并读同步状态；当前两者都走宿主重连方法 |
| `preferences` | `preferences` 对象 | 更新当前游戏本地偏好 |
| `direct` | `message` 对象 | 宿主代发私信；服务端另做类型和目标约束，并非任意私信出口 |
| `confirm` | `confirmation:{title,message,acceptText}` | 调用受信桌面确认弹窗，返回 `{confirmed}` |
| `self-reset` | `confirmationText:"确认删除"` | 账号数据重置流程，含二次确认约束 |
| `admin` | `command` 对象 | 仅服主；开服、搬迁及下列受限管理命令 |

`result`/`error` 后卡片应解锁相应控件；行动重复点击应使用待处理键去重。`idempotencyKey` 由客户端生成并和原请求一起重试；模型重试是新收费请求，应先确认并生成新键。联网异常时不要凭乐观本地画面删除重要状态。

## 5. 猎艳疆土行动接口清单

下面是当前 `submitIntent`/`applyIntent` 中的专用 `intent.type`，供分析和回归测试。坐标用 `x,y` 或 `to:{x,y}`，将领用 `generalId`；所有金额、归属、位置、库存和冷却由宿主判定，前端展示的预估不是权威结果。

| 分类 | 行动与关键参数 | 说明 |
| --- | --- | --- |
| 加入 | `prepare-join`（角色资料/偏好）、`join`（`previewId`） | 先生成预览，再确认加入；宿主可补玩家资料 |
| 地图/战报 | `quote-march`（`to,soldiers,generalIds,attack`）、`dismiss-battle-report`（`reportId`） | 报价只读；战报已阅 |
| 采集/练兵 | `start-mining`（`x,y`）、`stop-mining`（`jobId`）、`train`（`x,y,amount,mode?`） | 领地、资源、并发、金币、任务约束在引擎 |
| 修炼 | `cultivate-player`（`goldInvestment`）、`cultivate-general`（`generalId,goldInvestment,materialId?`） | 将领经验及状态由规则核验 |
| 部队 | `deploy-soldiers` / `gather-march`（`amount` 或 `mode:"max"`）、`march`（`to,soldiers,attack,expectedQuote`）、`cancel-march`（`jobId`） | 本地结算与云端持久化需区分，报价应与正式请求一致 |
| 将领位置 | `reorder-carried-generals`（`generalIds`）、`deploy-general` / `recall-general` / `take-general`（`generalId`） | 归属、当前位置、随行/部署/留置状态须一致 |
| 市场 | `list-general`（`generalId,price,sellerIntro?`）、`cancel-market-listing` / `buy-market-general`（`listingId`） | 交易会影响多方归属；不可单凭 UI 自行删记录 |
| 发掘 | `confirm-general-discovery` / `decline-general-discovery`（`discoveryId`） | 确认才进入模型生成链路 |
| 对话/外观 | `talk-general`（`generalId,topic,battleReportId?`）、`edit-general-appearance`（`generalId,note`） | 宿主调模型并校验；状态变更另有内部步骤 |
| 俘虏 | `execute-captive`（`generalId,allowFarewell,guidance?`） | 诀别信有额外生成链路 |
| 世界消息/信 | `world-chat`（`text`）、`generate-general-letter`（提案及目标等，详见服务） | 属于服务层特殊请求，不是 `applyIntent()` 通用行动 |

内部兼容和服务端自动步骤包括 `recover-defeated-player`、`power-train`（旧版）、`record-general-dialogue`、`surrender-general`、`apply-general-appearance`、`grant-general`；不能让编辑器把它们作为可任意提交的公开能力。实际入口、字段、返回效果要同时查 `electron/desktop/online-world/grid-conquest/game.js`、`electron/online-world-service.cjs` 和 `electron/grid-world-game.cjs`。

服主 `admin` 目前涵盖 `open-server`、`migrate-server`、`balance-update`、`scatter-treasures`、`player-reset`、`player-ban`、`player-unban`，以及受限的 `simulate-player-intent`（当前仅代目标玩家召回其已部署将领）。作者账号和本局权威设备等条件在宿主校验，不能仅靠按钮隐藏。

## 6. 云端记录、私有数据与操作队列

《猎艳疆土》当前线协议为 `§FYOW3§TYPE§ID§part/total§SHA256§base64url`。记录先规范 JSON、gzip，再分片写评论；新写单片最多 980 字符、最多 512 片、原记录最多 8 MiB。读入须按记录 ID、分片数、摘要、同作者及评论父子关系完整拼接；缺片、摘要错误和错误赛季都不能当作有效最新状态。

| 记录 | Schema | 用途 |
| --- | --- | --- |
| `CTRL` | `fyow.control/3` | 本作品本赛季控制记录 |
| `SNAP` | `fyow.snapshot/3` | 可回放的全局快照 |
| `MAP` | `fyow.map-delta/1` | 地图与公共状态增量 |
| `AUTH` | `fyow.authority/1` | 服主命令/平衡等 |
| `WCHAT` | `fyow.world-chat/1` | 世界通讯 |
| `DMWAKE` | `fyow.direct-wake/3` | 私信唤醒 |
| `RESET` | `fyow.reset/3` | 搬迁指引 |
| `INTENT`/`EVENT`/`VAULT`/`DIRECT`/`GDEF`/`GMEM` | 同名 `fyow.*/3` | 兼容、私有或将领记录，具体生命周期查服务代码 |

所有写入和删除应使用宿主持久化的顺序队列（现有 `cloudUploadQueue`），重启后重试、云端读回校验后再确认。删除仅限自身有确切 ID 和可验证替代数据的旧评论；评论根及回复的级联风险须保留。**不要因“0 秒”“看似已覆盖”或本地缓存缺少条目就删除云端记录**。将领换位置、市场转移、赛季更换，必须先确认新位置/归属的云端记录可恢复，再淘汰旧数据。不同账号、作品、赛季应有独立命名空间。

平台适配器由主进程持有，当前主要访问 `/console/api/comments/{workId}/1`（读、发、删本人评论）、聊天和消息接口、`/go/api/apps/{workId}`（作品详细介绍）、`/console/api/apps/{workId}/model-config/export` 及对应保存接口。它们是宿主内部平台请求，不是卡片可直接调用的公共 API；具体路径、负载、分页、回读与错误处理以 `electron/online-world-service.cjs` 的实现为准。

## 7. 可复现的制作与验收流程

1. **需求建模**：玩法状态、账号/作品/赛季作用域、谁能读写、哪些操作需要云端、哪些消耗积分、失败如何幂等重试。先写状态和事件 schema，再写 UI。
2. **实现宿主能力**：目前新玩法须先实现通用 SDK 或独立适配器与测试；不要把任意模型生成的规则代码放到主进程执行。把敏感账号与平台调用留在宿主。
3. **编写卡片**：单文件可运行前端、明确的 `postMessage` 消息、请求状态、错误/断线恢复；提示词和世界书各任务有可校验的输入输出。
4. **离线构建**：现有内置卡用 `npm run game:bundle` 生成包，`npm run game:card` 导出内置卡；`npm run game:library:refresh` 会遍历并重写 `game-cards/*.json` 中的程序，**只适用于同一猎艳疆土程序的多个服务器卡，不能用于异种游戏卡**。
5. **本机导入**：使用游戏库导入按钮、拖入 JSON，或将 JSON 放入安装包的游戏库目录；先执行卡包校验，再看是否识别作者及实际绑定作品。卡库随安装包的 `game-cards/*.json` 打包到 `game-library`，玩家自行导入的卡应保持独立。
6. **平台发布**：作品作者在受信工具里执行“更新云端储存”或使用经过核验的配置脚本。先读现有导出、合并目标字段、上传，再导出验证详细介绍信封、世界书和提示词；不要以本地 JSON 更新代表全服生效。对陌生作品先用测试作品演练，不拿生产作品试写。
7. **完整测试**：`npm test`、`npm run build`、`npm run verify:sandbox`；卡包导入/重启持久化、作者/普通玩家、旧 JSON 读新详细介绍、离线/重连、缺片评论、模型异常与重复收费、跨账号/跨赛季隔离、上传队列重启、迁移链及关键数据保留。
8. **版本发布**：内容仅改作品详细介绍且老客户端理解协议时可由作品更新传播；修改桌面宿主、规则、IPC、通用 SDK 或安全边界则需要新客户端。是否打包/上传 GitHub 是独立步骤，须明确要求和验收，不应从“卡内容更新”自动推断。

`npm run game:library:refresh` 是批量覆盖操作；在多游戏编辑器中应按单卡构建和发布，不扫描所有 JSON 重写为一个游戏。内置作品配置脚本 `scripts/configure-grid-companion-work.cjs` 支持核验模式 `FYOW_VERIFY_ONLY=1`，实际生产发布前先读脚本参数和现有作品配置。旧文档中的作品 ID、域名、哈希、客户端版本和平台页面步骤都可能已经过期，使用实时导出与当前代码确认。

## 8. 给下一次对话的编辑器任务边界

直接把本手册和 [游戏卡接口规范化与创作助手方案.md](游戏卡接口规范化与创作助手方案.md) 提供给下一次对话，并说明：

> 基于当前 `fyow.game-card/1` 的兼容事实，先设计并实现真正通用的卡片沙箱与 `fyow-host/2` 能力层，再制作模型辅助创作编辑器。编辑器让作者填写玩法目标、状态/事件 schema、UI 风格、模型任务及提示词；模型输出源码、结构化 manifest、世界书草稿和测试；通过静态检查、沙箱运行、权限/积分确认、模拟云端回放和人工预览后方可发布。保留《猎艳疆土》`/1` 适配器，不使旧卡失效。不要假定 `/2` 已实现，也不要用《猎艳疆土》的 `intent`、评论内部格式或 `fyow-grid-conquest` 来源标记充当通用 API。首次只在测试作品/测试账号发布，真实作品变更单独确认。

建议的通用能力边界：公开账号 ID/昵称投影、本游戏分区存档、受限公共记录、定向消息、经任务声明的模型调用、受信确认和音频/本地 UI 能力；邮箱、登录凭据、Token/Cookie、任意本地文件、其他作品数据和原始平台 HTTP 留在宿主。每项能力需要明确请求/响应 schema、作用域、体积/频率限额、幂等键、离线与重试规则、错误码、积分确认以及版本迁移测试。编辑器产出的代码一律视作不受信输入，不在主进程 `eval`。
