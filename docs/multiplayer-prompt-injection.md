# 多人会话提示词注入设计

## 平台字段与保存范围

平台作品页使用以下会话配置字段：

| 页面名称 | API 字段 | 用途 |
| --- | --- | --- |
| 提示词 | `pre_prompt` | 长期基础设定 |
| 前置词 | `pre_text` | 拼接到每轮用户输入之前 |
| 后置词 | `post_text` | 拼接到每轮用户输入之后，本次不修改 |

读取和保存均使用 `/go/api/apps/config`。房主工具会同时提交 `app_id`、当前平台 `conversation_id` 和 `is_global: false`，因此修改目标是当前会话配置，不是该作品的全局配置。

## 当前实现

0.10.6 加强名单格式约束：通用骨架要求名单由原作品的完整信息节点承载、保留必要父级和样式；专属名单规则必须具体指出渲染区块、锚点、承载结构、样式来源和动态用户名的内容位置。禁止在 HTML/XML 面板之间或渲染边界之外追加裸文本；Markdown 和纯文本各保留自身排版。没有固定标题、置顶要求或作品输出示例。生成器提示词见 `status-adapter-generator-prompt.md`，v2 协议保持不变，建议重新适配已出现名单裸露的作品。

房主收齐首轮输入、锁定成员后，在真正调用模型之前执行以下流程：

1. 如果是从未发送过消息的新会话，使用平台自身的发送与立即终止流程建立真实会话 UUID；平台没有独立的空会话创建接口。
2. 读取当前作品、当前会话的配置。
3. 保留用户已有的完整 `pre_prompt` 与 `pre_text`。
4. 删除旧的受控区块后，在 `pre_prompt` 最后写入唯一一份“多名独立真人用户设定”区块。
5. 删除旧的受控区块后，在 `pre_text` 最后写入唯一一份通用多人回复协议。
6. 保存为会话配置，重新读取并验证两个区块以及 `is_global: false`。
7. 删除第 1 步产生的初始化问答，再次验证会话配置仍然存在。
8. 重新载入后台作品对话页，确保下一次真实请求使用新配置。
9. 网络或平台保存失败时最多尝试四次；验证成功前不会把本轮真实内容发送给模型。

每轮开始前都会重新校验一次。玩家资料或名单发生变化时，只替换受控标签，不会在原提示词后重复追加。

房主发送给正式作品的每轮聚合输入是合法 JSON，顶层固定为 `Users` 数组；只含设定名和本轮原文：

```json
{
  "Users": [
    { "user-name": "玩家甲", "input": "向左走" },
    { "user-name": "玩家乙", "input": "观察四周" }
  ]
}
```

输入转换器只修改各项的 `input`，不会把平台账号 ID、骰点或未命中的其他结果发送给正式作品。

平台前端只有在当前 `conversation_id` 非空时才允许读取和保存会话配置。工具不会为了绕过这一限制而临时修改作品全局配置；新会话初始化也使用唯一标记并在写入成功后删除。立即终止通常不会产生完整回复，但最终是否产生极少量计费仍由平台的实时结算规则决定。

### 受控标签

前置词区块：

```text
<!-- MULTI_USER_TURN_PROTOCOL:BEGIN -->
<multi_user_turn_protocol version="1">
...
</multi_user_turn_protocol>
<!-- MULTI_USER_TURN_PROTOCOL:END -->
```

提示词末尾的玩家设定区块：

```xml
<!-- MULTIPLE_INDEPENDENT_HUMAN_USERS:BEGIN -->
<!-- 以下标签内记录的是同时参与当前会话的多名不同真人用户设定。每名用户仅由对应真人控制；模型不得主动扮演、代替、补写或决定这些用户的言行、思想、感受、选择与行动。 -->
<multiple_independent_human_users version="1">
  <human_user index="1">
    <name>玩家的设定名</name>
    <base_profile>玩家填写的身份、经历、性格、能力等基础设定</base_profile>
    <appearance>玩家填写的发型、五官、体型、服装等外观设定</appearance>
  </human_user>
</multiple_independent_human_users>
<!-- MULTIPLE_INDEPENDENT_HUMAN_USERS:END -->
```

姓名、基础设定与外观设定都会进行 XML 转义，玩家资料不能提前闭合标签或覆盖外层指令。

## 默认通用前置词的规则

当前默认前置词要求模型：

- 在作品原有结构允许的较靠前位置自然呈现完整名单，位置偏好低于原有结构完整性；不固定标题、列表语法或要求置顶，成员数据标签也不是输出模板；
- 按设定名区分每名真人用户本轮提交的行动或发言；
- 不代替真人用户补写台词、心理、感受、决定或行动；
- 若作品已有状态栏、信息栏、属性栏或角色面板，保留原模板和输出位置，并为每名在场用户分别输出一份；
- 若作品原本没有状态栏，则不凭空制造可能破坏作品格式的新状态栏。

这是保守的通用规则。它可以覆盖大多数作品，但无法知道某一作品状态栏的真实字段、HTML 结构、代码围栏或更新算法。

## 联机前置词适配

选择作品后、开房前可点击“一键适配联机前置词”。此操作会消耗积分，并要求该作品至少存在一个带 AI 回复的旧会话。

1. 工具通过平台会话列表寻找当前作品的已有会话，最多选择 5 份合格样本。
2. 对候选会话只读取最后一段非空 AI 回复的完整原文；不提交用户输入。包含 Google Generative AI 使用政策链接标记的回复会被排除，并继续向后寻找其他样本。
3. 工具在独立后台页面打开固定作品“多人联机状态栏适配器”，先切换到经过验证的纯净新会话，再以普通文本和独立代码块提交样本。
4. 适配器以 `fymp-prefix-adapter/v2` JSON 返回两条短规则：名单位置与呈现方式、用户状态位置与重复格式。不生成完整前置词，不提供输出示例或 UI 模板；名单规则必须给出稳定锚点和相对位置，状态规则必须给出原区域、最小重复单元、字段组织与用户名标识位置。
5. 工具验证建议的内容、长度和受控标记边界。只有新结果完全有效且平台已经为本次调用生成新会话编号时才替换旧适配；失败时旧结果继续保留。
6. 结果按目标作品 `app_id` 写入 Electron `userData/multiplayer-prefix-adapters.json`，不依赖缓存、会话名称或登录域名。
7. 开房后的会话配置注入由本地完成：通用骨架固定，作品专属的 `rosterRule` / `statusRule` 替换对应默认规则，只保留一组生效的位置与格式要求，不再次调用模型。v1 旧记录不删除但不再注入，UI 提示重新适配；未生成新版结果时使用新版通用规则。
8. 再次点击适配会重新读取所有会话、重新消耗一次积分并覆盖该作品的旧片段。

专属片段放在以下受控区块中：

```xml
<!-- WORK_SPECIFIC_MULTI_USER_STATUS_ADAPTER:BEGIN -->
<work_specific_multi_user_status_adapter schema="fymp-prefix-adapter/v2" detected_status_bar="true">
<participant_list_rule>作品专属名单位置与呈现规则</participant_list_rule>
<player_status_rule>作品专属用户状态位置与重复规则</player_status_rule>
</work_specific_multi_user_status_adapter>
<!-- WORK_SPECIFIC_MULTI_USER_STATUS_ADAPTER:END -->
```

生成器的完整提示词保存在 [status-adapter-generator-prompt.md](status-adapter-generator-prompt.md)，需手动更新到适配器作品。结构资料可以来自任意格式的旧回复；只描述实际存在的锚点和组织方式，不将样本当作续写或输出示范。结构完整性、共享状态只留一份及唯一标识引用由通用骨架负责。

0.10.4 同时修复独立视角在空白会话上重新启用时跳过写入的问题：已选作品但尚无会话 UUID 时，先复用初始化发送与立即终止流程建立真实会话，仅写会话前置词，读回验证后删除初始化问答并再次核验。操作期间锁定会话切换；关闭只删除本插件的标记块。未选择作品时仅保存启用设置，明确提示开局时写入，不假报已经插入。初始化可能产生平台计费，不会借用其他历史会话或改写全局配置。

## 边界与恢复

- 当前不会修改 `post_text`。
- 当前不会写访客端的自定义配置；模型交互仍只发生在房主端。
- 退出房间后不会删除受控标签，以便继续同一平台会话。下一次使用时会原位替换标签内容。
- 用户在标签外手动写入的提示词和前置词会原样保留。
- 如果用户手动删除标签，下一轮开始前会在字段末尾重新建立一份。
